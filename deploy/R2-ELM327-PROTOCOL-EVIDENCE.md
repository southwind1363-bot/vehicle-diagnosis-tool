# R2 ELM327汎用OBD消去: 通信根拠と実装境界

確認日: 2026-09-06。対象コード: 3.13.497 / e5ea41d3。本書は実行手順ではなく開発用の根拠記録。送信許可を変更しない。

## 確認した一次資料

[Elm Electronics ELM327DSL (v2.3), 98ページ](https://elmelectronics.com/wp-content/uploads/2020/05/ELM327DSL.pdf)。今回は公式配布のL版本文を確認した。2026年版規格、全互換アダプター、全車種の適合を示すものではない。以下のページはPDF内の印刷ページ番号。

| 箇所 | 確認できた事実 |
| --- | --- |
| p.37 Resetting Trouble Codes | 汎用消去はMode 04、対応する肯定応答は44。DTCに加えFF等の診断情報も影響する。永久DTC (Mode 0A) はこの要求で消去されない。確認はソフト側の責務。車両ごとの実行条件があり得る。 |
| p.41 Setting the Headers | 機能アドレスには複数のECUが応答し得る。物理アドレスとは区別される。 |
| p.43 Setting the Headers | 11-bit ISO15765-4の機能アドレスとして7DFを記載。全プロトコル共通値ではない。 |
| p.92 NO DATA | 待機時間内に応答を検出しなかった意味。受信フィルターで応答が見えない場合もある。 |

上記以外の内容は、以下では本プロジェクトの保守的な設計判断として明示する。規格本文の代替や、資料未確認の否定応答コード一覧は作らない。

## 現行コードとの不一致

- `script.js` の `WEB_SERIAL_READ_ONLY_COMMANDS` に04は含まれない。初期化はATH1/ATSP0を使い、表示用のECU選択を送信先選択に変換していない。
- `buildGenericObdDtcClearWorkflow` の `target.ecuId` は管理用参照であり、アドレス種別や送信先、実際に影響するECU集合の証明ではない。
- `createGenericObdDtcClearController` は同一メモリ内の最新状態だけを管理する。通信結果の信頼性、認証、保存完了、車両適合を証明しない。
- ローカルブリッジの `BLOCKED_WRITE_INTENTS` も消去を拒否する。既存読取経路に04を追加するだけの実装は行わない。

## 次の実装契約

以下は設計上の要求であり、未実装。

1. 送信先の範囲を明示する。transport、確定プロトコル、機能/物理の別、宛先、観測済み応答元を分離し、汎用OBDの機能要求を「選択ECUだけの消去」と表示しない。観測済みECU集合も影響対象の完全な一覧とは断定しない。
2. まず根拠と試験条件が揃う1経路に限定する。現時点で全9プロトコル、iPhone経路、J2534、ABS/SRS等の消去を同時に実装済み扱いしない。物理宛て消去の車種適合も別確認とする。
3. 各試行に一意のIDを付け、消去前保存、確認、接続世代、送信範囲を関連付ける。確認後の再接続・対象範囲変更・記録変更は再確認を要求する。
4. 永続的な消去前記録と開始記録を確認できなければ送信しない。ポート書込成功はECUの要求受理ではない。write開始後の例外、切断、timeout、応答破損は「未送信」ではなく結果不明として扱う。
5. 44の文字列部分一致で成功判定しない。該当試行の受信区間、プロトコルのフレーム境界、応答元、完全な応答データを検証する。古いバッファ、エコー、別要求の応答を除外する。
6. 肯定応答を受けても、機能要求の全対象が完了したとは断定しない。ECU別の肯定・不明を分離し、不明な応答を成功へ補完しない。NO DATAや中断後は自動再送しない。
7. 読取が安全に可能になってから保存/保留/永久DTCとreadinessを再取得する。未取得とコード0件を区別する。消去応答、再読取による変化、修理完了は別の状態にする。
8. 消去開始後の取消は、ECUで実行済みの処理を巻き戻す機能ではない。準備モデルのcancelを車両通信中の中止と共用しない。

## 模擬試験の受入項目

| 入力・状況 | 期待する扱い |
| --- | --- |
| 保存失敗、未確定プロトコル、古い接続世代 | 送信開始前に拒否。送信回数0 |
| 古い44、エコー、別要求データ中の44 | 該当試行の肯定応答としない |

| 二重クリック、確認後の再接続 | 同じ承認から二重送信しない |

これはテスト仕様であり、上記ケースの実装・合格記録ではない。

## 残る資料・実機確認

### 3.13.498 正規化済み応答の評価器

`evaluateGenericObdDtcClearResponses({ expectedSourceIds, frames, completion })` を独立した非送信APIとして追加する。sourceIdとpayloadは上流でフレーム境界を検証・正規化したものを受ける前提。生シリアル文字列、CANヘッダー、PCI、paddingの除去は扱わない。

候補応答元ごとに完全一致のpayload `[0x44]`、不明なpayload、無応答を分ける。不明な応答元も別一覧に残す。期待元が非空、収集完了、全期待元が肯定のみ、不明な応答元なしの場合だけ候補集合内の肯定観測フラグを立てる。timeout/切断/errorでは肯定フレームがあっても集合の完了フラグを立てない。これは全ECU消去や修理完了を意味しない。

入力制限は期待元32件、フレーム128件、payload1〜64byte、IDは空白・制御文字なしASCII1〜64文字。これは本APIの処理上限であり規格の最大値ではない。不正な型・余分な項目・疎配列を拒否し、結果は不変とする。実行・送信・再試行のフラグは常にfalse。

通常のデータプロパティのみを受け付け、getter/setter、非列挙・Symbolの余分な項目、配列の追加プロパティを拒否する。検証した値を内部へコピーし、元オブジェクトの再読込による判定の食い違いを防ぐ。

受信区間・古い応答・別要求・接続世代の検証は未実装の上流処理の責任である。正規化済みの偽データを渡すことは可能なため、この評価器の結果を実通信の証明として扱わず、現在の準備workflowにも接続しない。

対象車両/ECU/アダプターの識別、車種別の実行条件、アドレス範囲、実フレーム例、否定応答/応答保留の対象規格、待機期限、保存・再読取の実測が必要。パスワード解除や廃車予定という条件だけでは代替しない。実車試験は接続前に利用者へ範囲とリスクを提示し、その車両での実施判断を受ける。

合成データの評価器に続く工程は、試行と受信区間の関連付け、送信範囲、永続記録の契約設計である。評価器だけで実送信へ進まず、上流の検証を設計レビューする。一般利用者向け消去ボタンはその後の段階。
