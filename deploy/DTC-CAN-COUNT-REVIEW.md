# Web SerialのCAN DTC件数バイト修正案

確認日: 2026-10-17。確認後、本体3.13.695へ適用。

## 適用結果

11bit CAN単一フレームの通常Web Serial変換処理だけへ修正を適用した。現行本体と固定した旧関数を比較する検証162項目が合格。P0300・P0420の複数ECU応答、2件応答、重複コード枠の拒否も確認した。通常取得の模擬正常応答を件数付きへ更新し、件数なしの不正例は専用拒否検証に残す。

統合試験で、後続PID読取時の蓄積原文再解析が一般decoderへ戻り、修正済みDTCを失う経路も確認した。retainObdDeveloperReadout内で過去のDTC応答にも同じWeb Serial変換を使い、今回の取得・失敗による上書きを優先する。通常テキスト取込には適用しない。通信統合3,991項目が合格し、03/07/0Aの複数ECU・後続読取・切断復帰・JSON保存復元を含む。

Chromeで修正後の本体変換処理へ模擬CAN応答を渡し、その結果を実ファイル選択で取り込み、JSONの実ダウンロード・再取込後もP0300/P0420を保持した。救出保存の6禁止状態・2保存開始失敗・再試行も合格。ブリッジ検査は初回localhost接続がEACCESとなったが、制限外の模擬検査384項目はエラー0。オフライン183項目とデータ検査（203 JSON・3,878 DTC）はエラー0。

診断主検査7,447項目は修正後の再実行でエラー0。全体起動の補助検査はNO DATA復帰まで合格した。初回は検査中の本体編集によりファイル不変チェックが失敗し、再起動した。続いて旧CAN模擬応答と構造確認用の期待文字列を更新したため、主検査を補助importから分離して再実行した。更新前の主検査が重複実行していたプロセスは、更新後の主検査の合格確認後に停止した。単一の全体起動の成功ではなく、補助検査と更新後主検査の合格として記録する。

保存schema、既存保存記録、一般decoder、29bit・複数フレームの挙動は変更しない。対象外経路のDTC件数処理は引き続き点検が必要。実機・実車・ドライバー通信の検証はしていない。以下は適用前の問題と提案の記録。

## 再現した問題

通常Web SerialのbuildWebSerialDtcResponseOverridesはCAN単一フレームのPCIとpaddingを除くが、DTC件数を除かずdecodeObdDtcResponseへ渡す。一般decoderはservice直後から2バイトずつコードとして読む。限定評価器の件数契約を緩める問題ではなく、通常経路で形式を区別する必要がある。

| 11bit CANの応答例（ECU・PCI・本文・padding） | 現行通常経路 | 修正案 |
| --- | --- | --- |
| 7E8 02 43 00 AA AA AA AA AA | 未解析 | 取得済み・0件 |
| 7E8 04 43 01 01 33 AA AA AA | 未解析 | P0133・1件 |
| 7E8 04 43 01 03 00 AA AA AA | P0103と誤読 | P0300・1件 |
| 7E8 03 43 00 00 AA AA AA AA | 取得済み・0件 | 件数と本文長が一致せず未解析 |
| 7E8 04 43 02 03 00 AA AA AA | P0203と誤読 | 件数不足で未解析 |

前回の統合試験で使用した43/47/4Aの後の0000は、CAN件数付き本文の正しいゼロ件例ではなかった。一般decoderの挙動を再現する入力として残せるが、CAN正常応答の根拠には使わない。

## 根拠と確信度

- [Elm Electronics ELM327DSL v2.3](https://www.elmelectronics.com/wp-content/uploads/2020/05/ELM327DSL.pdf) 印刷36ページを再確認。非CANのコード対と異なり、ISO 15765-4ではservice直後にDTC件数が入る。
- [Scapyの公式services.py](https://github.com/secdev/scapy/blob/master/scapy/contrib/automotive/obd/services.py) を2026-10-17に再確認。03/07/0Aの肯定応答はcountとDTCリストを持つ。

ローカル実装の誤読再現に対する確信度は高い。公開資料と公開実装による限定的な構造確認であり、最新規格全文への適合、互換VCI、全車種、実車での動作を証明しない。

## 適用候補の範囲

開発専用の[scripts/validate-dtc-can-count-proposal.js](scripts/validate-dtc-can-count-proposal.js)に、現行関数と候補関数の比較を実装した。候補はVM内だけで差し替え、本体ファイルは変更しない。

1. Web SerialでECU番号付き11bit CAN単一フレームとして識別され、PCIで本文を切り出せる03/07/0Aに限り、serviceの次を件数として読む。
2. 本文長が2 + 2 × 件数に一致し、コード枠が非ゼロ・重複なしの場合だけ採用。件数0は一般decoderへ渡す内部表現でゼロ件へ変換する。原文の書換え・保存は行わない。
3. 件数不一致・不正なコード枠は未解析にし、0件や別コードとして表示しない。
4. ヘッダーなし・29bit・複数フレーム・一般decoder・ブリッジ取込は今回の候補適用範囲外。特に対象外経路の正しさや完全性は本提案の検証で保証しない。続く別点検が必要。
5. 保存schema、既存保存記録のコード、限定評価器の受入条件、通信コマンド許可を変更しない。実行許可を付与しない。

## 検証と適用条件

現行/候補を、保存・保留・永久DTCそれぞれで、空白あり/compactの両方から呼び出す。ゼロ件、P0133、P0300、件数なし、件数不足、0000コード枠の36ケースと、ヘッダーなし・NO DATA・否定応答の互換性を確認し、153項目が合格した。これは修正案の比較試験であり、本番修正や実車試験の完了ではない。

適用すると診断コードと取得済み判定が変わるため、この具体的範囲の確認後に本体へ反映する。反映時は既存のCAN模擬正常応答を件数付きへ直し、件数なしの旧例は拒否用として保持する。通常読取・複数ECU・保存復元の回帰検証、本体版とオフライン資産の更新、公開確認まで行う。過去に誤読して保存したコードは自動で推定修正しない。
