## 採用する画面構造

以下は本ツールの設計方針。見た目だけでなく、この導線で実際の通信と結果確認を完結させる。

```text
ホーム
  車両診断 -> 車両選択/識別 -> 接続確認 -> 全体スキャン / ECU選択
    ECU一覧 -> ECU機能 -> DTC / データ / ECU情報 / 作動テスト / サービス
      DTC一覧 -> DTC詳細・FF -> 診断支援 / 消去前確認 -> 再読取
      データ項目選択 -> 数値・グラフ -> 記録 -> 再生・比較
  汎用OBD -> 接続確認 -> DTC / データ / FF / readiness / ECU情報
  整備サービス -> 車両・対象ECU確認 -> 適合機能 -> 条件確認 -> 実行・終了確認
  保存記録 -> セッション -> 結果・記録再生・整備前後比較・レポート
  設定 -> VCI / 表示 / オフライン更新
```

- 1画面は1つの作業目的。長いページに車両設定、結果、ロードマップを全部並べない。表と操作バーは同じ画面で扱ってよい。
- 上部に車両・ECU・接続状態、下部に戻る・ホームとその画面の操作を置く。戻っても選択と取得結果を保持する。
- タブレットのタッチ操作を優先し、主要操作は48px以上を目安にする。横画面と縦画面、小さい端末で文字切れ・重なりを検証する。
- 中立色の外枠、読みやすい明暗のデータ面、限定した状態色を使う。状態は色だけに依存させない。大きな広告風見出しや説明カードを置かない。
- ECU未応答、未実施、非対応、確認済み0件を区別する。取得時刻、単位、更新停止を表示し、古い値をライブ値と誤認させない。
- 通常画面から進捗率、内部契約、検証件数、開発トークン入力を除く。開発画面は別入口にし、画面を隠すことと実行権限の制御を混同しない。
- 故障原因の推定は取得事実の詳細から開く。推定をECUの回答と混ぜず、既存診断ロジックはUI移行のために簡略化しない。
- 未実装機能の大量の無効ボタンは並べない。適合や接続条件で使えない機能は理由を示し、開発計画は開発側で扱う。

| R3 J2534診断 | Windowsで対象ECUの読取、ECU一覧、適合に基づく全体スキャン | 実DLL識別、車両チャンネル、要求/応答、終了を統合。まず確認対象1ECU、その後複数ECU。応答の所属と時間切れを検証 |
| R4 整備サービス | 適合したEPB、ABSエア抜き、アクティブテスト等を機能単位で提供 | 車種/ECU/機能ごとの要求、条件、段階操作、終了/復旧、ログ、再確認を実装し試験。車両試験の最終判断は利用者 |
| R5 対応車拡大 | 車種別データリスト・サービス、現行車通信、整備前後比較の充実 | 出典と実測を適合表へ記録。通信可能と診断/サービス対応を別判定。機能単位の回帰試験と実車実績を更新 |

R1で数値表示・項目選択・基本グラフ・記録再生を一巡させる。高度なトリガー、長時間比較、簡易メーター装飾は後続とし、初回の利用開始を妨げない。

R3のPCドライバー接続実装はR1/R2と並行する。R4の仕様・状態遷移・模擬検証も先行し、実車実行だけを該当transportと適合確認に依存させる。サービスの着手順は資料と試験車両の揃う順で決め、EPB等を一律に低リスクとは扱わない。

## 変更・試験方針

### 表示整理と診断支援の改善

通常画面の静的な説明・英語の小見出し・重複見出しを減らす。通信異常、未取得、実行条件、操作直前の重大な警告は一括非表示にしない。警告ごとに常時表示/操作時表示/詳細表示を棚卸ししてから変更する。

診断支援は「大量の点検一覧」から「次に確認すべき点検と、その結果による分岐」へ改善する。R1の画面一巡を優先し、その後に取得事実と診断支援を接続する工程で扱う。既存候補は削除せず詳細に保持し、根拠不足時は識別力のある追加質問・測定へ進む。

この診断支援変更はSolでの設計・レビューを必要とする未着手項目。着手前に原因候補順位、停止条件、問診、履歴・保存互換への影響を説明する。複数DTC、矛盾する事実、情報不足、未取得、確認済み点検、重大故障の優先表示を回帰試験に含める。UI整理の名目で診断ロジックを簡略化しない。
