# ライブ値の取得集計・保存比較キー v2 移行

2026-10-11 / 本体3.13.662 / 承認後に適用

## 旧版3.13.661で再現した問題

同じengine_speed・ECU 7E8・rpmで経路だけがCAN&#124;AとCAN Aの場合、buildCoreReadoutInventorySummary は異なる2行に同じキーを作る。countsById.live_pid_snapshot は2だがlivePidValueCountとlivePidValueKeys.lengthは1になる。

さらに同じ暖機条件・同じprotocolの記録で、片方の経路の1200 rpmと他方の2400 rpmを与えると、buildImportedCoreReadoutInventoryComparisonSummary が比較可能とし、差分行を1件生成する。これは固定入力での再現であり、実車結果ではない。

バス・チャネル・ゲートウェイ経路の縦棒/空白と、欠落/文字列ハイフンの6種類を両方向で再現した。ライブ表示や時系列グラフの既存修正とは別に、取得集計と保存比較のキーに残る問題。

## 適用した形式

ライブ値キーに live_pid_value_v2: という接頭辞を付け、内容をJSON配列にする。

    [id, sourceEcu, unit, numericValue, networkBus, networkChannel, gatewayRoute]

欠落はnull、文字列ハイフンは文字列のまま保持する。経路は既存の正規化結果を使い、全半角/大小文字だけをそろえる。文字列中の縦棒はJSONのUnicodeエスケープで保存する。旧形式の区切り解析が偶然v2を有効なキーと読まないよう、キー内に生の縦棒を含めない。

例の結果: 同じ値・別経路の2行は別キー2件。同じ経路の1200→2400は比較可能。異なる経路同士は数値差分の対象外。

## 移行時の扱い

1. ライブ値・取得済みECU経路・未解決ECU経路の識別形式をまとめて版管理する。既存のcamel/snake aliasは対で維持する。
2. v2同士は、値以外の測定項目・単位・ECU・経路が一致する場合だけ比較する。既存の取得状態・観測条件・protocolなどの判定を引き続き必須とする。
3. 旧形式とv2の混在は比較不可とし、「差分なし」とは扱わない。旧形式のキーだけから失われた縦棒や未指定情報を復元しない。旧形式同士の経路付き数値比較も、衝突が解消したとは扱わない。
4. 元の測定行と通信経路が保存されている場合は、新しい取込処理でv2の現在集計を作る。保存されていた旧集計との比較は版不一致として扱う。元情報がない記録へ経路を推定しない。
5. 取得値そのもの・RAW・通信許可は維持する。実車送信の許可にはしない。

集計生成、キー解析、比較、alias正規化、JSON保存復元、差分の画面表示を一体で変更した。ライブ値以外のFF/ECU情報/Readiness等のキー移行はこの案の対象外で、別途点検が必要。

## 作成済み・検証済み

node deploy/scripts/validate-inventory-live-key-v2-proposal.js

344項目合格。旧版の出力を固定fixtureとして保持し、本体の集計・比較で6種類×両順序、同一経路比較、部分取得、版混在拒否、JSON保存復元、表記揺れ、矛盾、不正キー・数値を確認した。経路未指定の旧形式同士の比較は維持するが、旧経路付き形式同士は比較しない。正規化で長さ上限を超えた経路は比較キーから除外し、元の測定行は保持する。

通常のライブ値画面に、旧形式等では比較不可であり差分なしではない旨を表示する。比較可能な場合は項目・ECU・経路ごとの前後値と差を表示する。実機試験や全車種適合の確認ではない。

## 適用範囲

保存されるライブ値の派生キーと比較可否の変更はユーザー確認後に適用した。測定データ・RAW・通信許可は維持する。他の読取種別のキー点検は別工程として残る。
