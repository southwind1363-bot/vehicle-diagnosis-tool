# ライブPIDの経路継承・照合修正（承認済み・本体適用）

2026-10-11 / 旧版3.13.660 / 適用版3.13.661

## 再現した問題

normalizeBridgeLivePidSnapshot が、同じECU 7E8についてバスCAN&#124;AとCAN Aを同じ候補経路として数える。共通キーが縦棒を空白に置換し、欠落欄と文字列ハイフンを同一扱いするため。

模擬入力: 経路未指定の上位ライブ値9999 rpmと、経路付きのECU記録1200/2400 rpmを同時に与える。

| 条件 | 旧版3.13.660 | 3.13.661 |
| --- | --- | --- |
| 上位値の経路未指定、候補経路がCAN&#124;AとCAN A | 候補を1経路と誤認し、9999に片方の経路を継承して採用 | 経路を推定せず、明示された1200/2400を採用 |
| 上位値はCAN A、取得済みECU記録はCAN&#124;Aのみ | 別経路の9999を採用 | 不一致として除外し、経路付き1200を採用 |
| 候補が本当に1経路 | 経路を継承 | 既存動作を維持 |
| 通常の異なる経路A/B | 1200/2400を採用 | 維持 |

実車の観測結果ではなく、再現用の固定値。入力自体は書き換えず、ECU別の記録も保持する。

## 修正範囲

normalizeBridgeLivePidSnapshot の1関数内に限定する。

- 経路未指定値の継承候補を数えるキーに、既存の損失のないJSON配列キー getDtcReadoutNetworkScopeIdentity を使う。
- 取得済みECU記録と上位値の照合にも、同じ経路キーを使う局所的な照合関数を置く。
- 全半角/大小文字の正規化、矛盾の照合拒否、照合元が経路未指定の場合の既存方針を維持する。

共通キー、他の正規化関数、取得充足度のキー、保存schemaは変更しない。RAWの換算や通信許可も変更しない。

## 検証

node deploy/scripts/validate-live-scope-inheritance-proposal.js

133項目合格。適用前は隔離VMで比較し、適用後は旧版の正規化結果を固定fixtureへ保存して、本体コードの回帰試験へ切り替えた。

- バス/チャネル/ゲートウェイの縦棒と空白、欠落と文字列ハイフンの6種類を双方向で再現。
- 経路未指定の誤継承と、明示された別経路値の誤採用を除外。
- 正しい値・経路、ECU別記録、入力不変、通信禁止を確認。
- 通常の単一/複数経路、表記揺れ、矛盾、blocked/失敗/送信フラグ、RAWの動作を比較。
- 本体の正規化結果を診断sessionへ組み込み、実JSON保存・復元で値と経路を確認。

既存挙動: 子ECU内で1から始まるsourceLineはJSON取込で全体の連番へ振り直される。この差は現行の通常A/B経路でも再現し、検証ではその既存差だけを許容した。全入口でメタデータが完全一致するとは扱わない。

ブラウザー本体でブリッジ応答を正規化し、実JSON取込で1200/2400の表示と9999の除外を確認。390/1280px・明暗表示・保存復元も合格（readiness-review-JfAetv）。実機/VCI通信は未実施。

## 適用確認

採用されるライブ値とその件数・経路、そこからの派生表示/分析が変わるため、診断結果の契約に関わる。具体例は9999の1行から、明示された1200/2400の2行への変更。保存schemaは同じだが再取込結果は変わり得る。利用者の「続けて」による適用確認を受け、3.13.661へ反映した。既に誤った経路を付けて保存された記録を、この変更で自動訂正できるとは扱わない。

全体OBD7,447項目、ブリッジ384、オフライン183、端末起動1,369、配布766項目はエラー0。851ファイルのZIP別展開とローカルHTTP5資産の内容一致を確認。
